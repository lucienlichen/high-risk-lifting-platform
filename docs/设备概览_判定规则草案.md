# 设备概览判定规则草案

范围只含六项服务：安全监控、健康监测、健康评估、裂纹预测、故障诊断、风险定量评估。点巡检、检验、维修等不进入首页。

规则从当前代码抽出，不是现场规程。后面的「统一规则」和「事故映射」是草案，供讨论，不能当成已经确认的业务口径。

## 先说清两套口径

现有列表和详情把状态写成健康 / 亚健康 / 异常 / 高风险 / 低风险，而且多项规则一叠加，安全监控和结构评估会几乎全红。首页如果直接用这套结果，车间图没有区分度。

概览页因此另用本文的统一规则生成演示灯：每项服务只出正常、黄、红，设备取最严重的一项。分布是大部分正常、少量黄、很少红。旧页面没有改，所以列表上的「几乎全报警」和概览灯不会一致。是否废弃旧口径，需要单独定。

会议纪要写的是「黄色（报警）和红色（预警）」。这和常见习惯相反：常见说法里红更严重，黄是预警。本文和概览页按纪要用字（黄 = 报警，红 = 预警），并在页面图例里标了「措辞待确认」。是否对调，需要业务负责人确认。

## 统一规则（提案）

每台设备、每项服务输出一盏灯：

| 灯 | 纪要用字 | 含义（草案） | 首页怎么表现 |
|---|---|---|---|
| 正常 | — | 这项没有需要处理的偏离 | 磁贴压暗，小灯不亮 |
| 黄 | 报警 | 接近限值或早期劣化，要关注 | 黄磁贴靠前 |
| 红 | 预警 | 超限、联锁异常或高风险，要处置 | 红磁贴最前 |

设备综合灯 = 六盏灯里等级最高的一盏。并列时按服务顺序取说明：安全监控、健康监测、健康评估、裂纹预测、故障诊断、风险定量评估。

概览页的具体分档（演示用，阈值仍待定）：

| 服务 | 黄（报警） | 红（预警） |
|---|---|---|
| 安全监控 | 力矩或风速、偏斜达到限值的约 70%–100%，尚未超限 | 超限，或抗风防滑、起升限位等联锁报警 |
| 健康监测 | 测点预警 | 测点异常 |
| 健康评估 | 结构亚健康，或损伤轻度 | 结构异常，或损伤中度及以上 |
| 裂纹预测 | 预计萌生约 7–12 个月 | 预计萌生不超过约 6 个月 |
| 故障诊断 | 任一部件亚健康 | 任一部件高风险 |
| 风险定量评估 | 综合分进入中风险段（草案暂按 26–40 分） | 高风险段（草案暂按 41 分及以上） |

现有代码里的风险分段是另一套（见下文），不能直接等同于黄、红。

## 四大事故映射（草案）

只作为概览上的事故标签，方便从红黄设备想到可能事故。不是鉴定结论。

| 事故 | 主要来源（草案） |
|---|---|
| 钢水包倾覆 | 安全监控里的超载、力矩、运行偏斜；起升减速机诊断；制动器早期磨损 |
| 焊缝开裂 | 结构应力和声发射监测；结构健康评估里的主梁损伤；裂纹预测 |
| 倒塌 | 主梁、支腿、端梁的结构评估；风速和抗风防滑；行走车轮、轨道 |
| 坠落 | 制动器高风险；起升减速机高风险；起升高度或下降深度限位 |

一台设备可以因不同服务带上不同事故标签。综合标签取最严重那一项服务上的事故。风险定量评估的指标偏管理和使用条件，和某一类事故没有直接机理，草案里只按「哪项指标最高」临时挂一个事故，需要领域专家改。

## 1. 安全监控

代码里没有单独的「安全监控」等级函数。列表和详情是两套规则。

### 列表

位置：`src/views/scene/SceneView.vue` 的 `buildSafetyRow`（约 1063–1087 行）。

输入：

- 电控看板 `getRemoteMonitoringData` 的限位、运行参数、三相电流（`src/mock/remoteMonitoring.ts` 约 193–276 行）
- 设备是否在线、`status`、`riskLevel`（`src/mock/index.ts` `riskFromId` 约 436–438 行：编号字符和 mod 100，`<58` 正常，`<79` 低，`<92` 中，否则高）

阈值和输出：

- 限位：每个限位 `0–99` 的随机数 `> 8` 才算正常，否则异常（约 271–273 行）。大约 9% 的限位会异常。
- 运行参数：列表用 `item.status !== 'normal'` 计数（约 1068 行）。运行参数对象只有名称和数值，没有 `status`。运行时这项恒为真，10 个运行参数全部计入报警次数。
- 电流：任一相解析值 `≥ 200 A` 计 1 次（约 1069–1070 行）。生成范围大约是 12–188 A（约 239–243 行），这项实际上到不了 200。
- 监控系统状态：在线且报警次数 `< 2` 为正常，否则异常（约 1073 行）。由于运行参数被全部计入，报警次数远大于 2，结果几乎总是异常。
- 预警状态：报警次数 `> 0`，或设备 `riskLevel === 'high'`，则显示「报警」，否则「正常」（约 1074、203–206 行附近的列）。同样几乎总是报警。
- 作业状态：运行中、在线，且另一枚种子 `< 82` 为作业中（约 1072 行）。这是作业，不是报警等级。

详情里的单次吊重另有状态：`src/mock/remoteMonitoring.ts` 约 497 行，`r < 75` 正常，`< 92` 预警，否则报警。列表不用它。

### 详情（GB/T 28264 参数）

位置：`src/components/DeviceMonitoringWorkspace.vue` 约 75–114 行着色，约 700–801 行造数。

| 量 | 黄 | 红 | 备注 |
|---|---|---|---|
| 起重量 / 力矩 | 力矩百分比 `> 85` | `> 100` | 造数时载荷不超过额定的 85%，再加减 8 个百分点，超限不常见 |
| 大车运行偏斜 | `> 限值 × 0.7` | `> 限值` | 限值写死 10 mm（约 742 行） |
| 风速 | `> 限值 × 0.75` | `> 限值` | 限值写死 10.8 m/s（约 741 行），造数上限 9.5，红灯很难出现 |
| 幅度 | 无黄档 | 大于限值 40 m | 桥机演示把幅度标成不适用 |
| 抗风防滑、超速、门限位、联锁等 | 无黄档 | 布尔量直接「报警 / 异常 / 故障」 | 约 794–801 行，多数 `> 0` 即正常，大约一成会坏 |

开放问题：

- 列表把没有状态的运行参数全部算成报警，这是不是笔误？若是，线上「几乎全报警」就是这个原因。
- 接近限值的比例，纪要和设计稿都还没定。详情用了 70%、75%、85% 三套，互不相同。
- 列表的「报警」和详情的红黄没有合成一盏设备灯。

## 2. 健康监测

位置：`src/views/scene/SceneView.vue` `buildHealthRow`（约 1094–1115 行）。

输入：是否在线；应力、损伤、钢丝绳、电控看板、减速机、制动器、车轮数组是否非空；种子 `hash(seed + salt) % 100`。

阈值和输出（只有正常 / 异常，没有黄）：

- 离线，或该类没有数据：异常。
- 在线且有数据：种子 `< 8` 为异常，否则正常。结构、电控、减速机、制动器、车轮各自独立，大约 8%。
- 监测中 / 未监测只看是否在线（约 1109 行）。

测点总表在 `src/mock/remoteMonitoring.ts` `getDeviceMonitoringPoints`（约 542–546 行）：`< 78` 在线，`< 92` 异常，否则离线。这张表不驱动健康监测列表。

监测曲线上的点状态是 `statusFromRng`（约 132–137 行）：`< 72` 正常，`< 92` 预警，否则报警。健康监测列表没有使用这三档，只用上面的 8% 异常。

开放问题：

- 列表只有正常/异常。概览要的「测点预警 = 黄、测点异常 = 红」在列表里没有对应字段。
- 制动器和钢丝绳在监测数据里是占位，状态被写成正常（`placeholderItem`，约 184–190、423–429 行），但列表仍可能把它们随机标成异常。两处不一致。

## 3. 健康评估

结构损伤度：

- 列表：`src/views/scene/SceneView.vue` `damageLevelOf`（约 1281–1285 行），`buildStructureAssessmentPoints`（约 1305–1362 行），`buildHealthAssessmentRow`（约 1396–1413 行）。
- 详情：`src/components/HealthAssessmentDrawer.vue` `damageLevel`（约 227–231 行），公式与列表相同（约 301–308、349–355 行）。

输入：应力测点 24 小时曲线的峰值、幅值、趋势，以及该测点的 `status`；另外 14 个孪生位置用另一套公式。

损伤度（夹在 0.12 和 0.96 之间）：

- 实测：`峰值比 × 0.42 + 幅值比 × 0.28 + 趋势比 × 0.12 + 状态权重 × 0.18`
- 状态权重：报警 1，预警 0.72，正常 0.4（约 1325 行）
- 孪生：`峰值比 × 0.42 + 幅值比 × 0.28 + 0.38`（约 1352 行）。常数 0.38 会把大量孪生点抬到 0.7 以上

分档：

| 损伤度 | 等级 | 列表/详情用字 |
|---|---|---|
| `≥ 0.85` | danger | 异常 |
| `≥ 0.70` | warn | 亚健康 |
| 其余 | normal | 健康 |

结构对象（主梁、支腿、端梁、运行机构、附属结构）取组内最坏点。设备的「金属结构」再取全部点的最坏值。因为孪生公式带 0.38，结构列很容易是异常。这和线上「金属结构几乎全异常」一致。

电控健康：任一限位 `ok === false` 就是异常，没有亚健康（约 1409 行）。限位大约 9% 异常、共二十多项，电控列也会几乎全异常。

减速机、制动器、车轮：取监测点 `status` 的最坏值。点状态来自 `statusFromRng`，不是温度或振动阈值。

结构损伤详情（声发射）不按应变数值分档，直接沿用监测点状态，再配一个展示用百分比（`src/components/HealthAssessmentDrawer.vue` 约 532–537 行）：

| 点状态 | 损伤程度 | 百分比 |
|---|---|---|
| 正常 | 无 | 4%–9% |
| 预警 | 轻度 | 28%–45% |
| 报警 | 中度，百分比 `≥ 78` 时写成重度 | 58%–87% |

开放问题：

- 0.70 和 0.85 是演示分档，没有对应规范条款。
- 孪生公式的 `+ 0.38` 使「几乎全异常」成为结构问题，还是故意的演示效果？
- 轻度 / 中度要对应黄 / 红，但百分比是状态算出来的，不是反过来用百分比判定。

## 4. 裂纹预测

位置：

- 列表 `buildCrackRow`、`formatPredictedCrackTime`：`src/views/scene/SceneView.vue` 约 1371–1438 行
- 详情同一公式：`src/components/CrackMonitoringDrawer.vue` 约 174–191 行
- 着色：同文件约 44–45 行，看的是损伤度，不是月数

输入：上一节的损伤度和 `工作小时 = floor(损伤度 × 48000)`。

剩余寿命：`工作小时 × (1 - 损伤度) / 损伤度`，再换成文案：

| 条件 | 文案 |
|---|---|
| 损伤度 `≥ 1` | 已萌生（公式把损伤度夹在 0.96 以下，列表里到不了） |
| 损伤度 `≤ 0` | 大于 10 年（下界是 0.12，也到不了） |
| 剩余小时 `≤ 24` | 24 小时内 |
| 剩余天数 `≤ 30` | 约 N 天 |
| 剩余月数 `≤ 12` | 约 N 个月 |
| 否则 | 约 N 年，超过 10 年写成「大于 10 年」 |

详情可选算法系数：模型 02 × 1.1，模型 03 × 0.9，再夹到 0.10–0.99（约 225–226 行）。列表不用这个系数。

红橙色：损伤度 `≥ 0.85` 红色，`≥ 0.70` 橙色。走查里「约 9 个月红、11–12 个月橙」是损伤度算完以后的观感，代码没有「≤6 个月红、≤12 个月黄」这条规则。

开放问题：

- 概览草案用的 6 个月 / 12 个月，和现码的 0.70 / 0.85 不是同一条线。要哪条，需要定。
- 列表取最短的一个点。设备灯是否也只看最短点，还是任一结构对象越线就算。

## 5. 故障诊断

列表：`src/views/scene/SceneView.vue` `buildFaultRow`（约 1520–1555 行）。

输入：减速机、行走车轮、制动器监测点的 `status`（正常 / 预警 / 报警）。

输出：

- 三个部件各自取最坏点，整机再取最坏部件。
- 用字：danger = 高风险，warn = 亚健康，normal = 健康（约 993–996 行）。
- 部件不是正常就写成「有故障」，不区分黄和红（约 1552–1554 行）。
- 说明文字按最坏部件和等级从固定段落里取（约 1456–1507 行），所以同一等级的设备文案相同。

监测点等级仍是 `statusFromRng`（约 72% 正常、20% 预警、8% 报警），没有温度、声级、振动的数值门槛。

制动器在监测数据里被占位成恒为正常，所以列表里的制动器「有故障」基本不会出现。详情 `src/components/FaultDiagnosisDrawer.vue` 约 460 行另起一串随机数：`> 0.88` 高风险，`> 0.7` 亚健康，否则健康。列表和详情对不上。

开放问题：

- 亚健康 = 黄、高风险 = 红，是否接受。
- 制动器以哪边为准。
- 「有故障」要不要拆成黄故障和红故障。现在列表把两档都叫有故障。

## 6. 风险定量评估

位置：`src/mock/riskAssessment.ts`。

输入：15 项指标。每项 4 个等级，设备编号种子在 1–4 里均匀抽取（约 207–211 行），不是按真实人数、年限或检验记录套档。

综合分 = 15 个等级之和，范围 15–60（约 212 行）。

分段（`levelFromScore`，约 196–200 行）：

| 综合分 | 代码用字 |
|---|---|
| `≤ 25` | 低风险 |
| `≤ 35` | 一般风险 |
| `≤ 45` | 较大风险 |
| `≥ 46` | 重大风险 |

列表 `buildRiskRow`（`src/views/scene/SceneView.vue` 约 1579–1596 行）只展示分数、4 级指标个数和指标名，并按分数排名。列表本身没有黄红。

详情矩阵把命中的那一格着色，其余格仍显示门槛文字。综合分 18 在这套随机规则里可能出现，但不是默认值。线上走查「多为 18」更像另一版把分数写死了。

「使用场所」选项本地已改成生产区域（约 52–58 行）。线上截图仍是建筑工地 / 公共场所那一版。

开放问题：

- 中风险、高风险对应哪几段？草案暂把一般风险的上沿 26–40 当作黄、41 分以上当作红，和代码里的四档并不重合，必须改完再编码到正式规则里。
- 15 项里哪些算冶金事故的驱动项，哪些只是管理条件。现在的事故标签是临时的。
- 等级是随机抽的。正式规则应按指标定义回填，而不是保持均匀随机。

## 和概览页的关系

`src/mock/overviewStatus.ts` 实现的是上面的统一规则草案，用设备编号做确定性抽签：大约 89% 全正常，大约 9% 恰有一盏黄灯，大约 1%–2% 有红灯。它不调用本节列出的旧函数，避免首页被旧的「几乎全红」淹没。概览三页只读这份结果和设备台账，不采用设计稿里的占位条数。

因此现在同时存在三层：

1. 旧列表 / 详情：本节摘出的规则，问题是口径分裂、演示偏红。
2. 统一规则草案：正常 / 黄 / 红，设备取最坏，黄 = 报警、红 = 预警（待确认）。
3. 概览演示数据：按草案点灯，但阈值句子是写好的示例，不是把旧公式算完再套档。

要把第 3 层换成第 1 层的真实计算，需要先关掉安全监控列表的运行参数误计，并给裂纹月数、风险分段一个确认过的黄红门槛。
