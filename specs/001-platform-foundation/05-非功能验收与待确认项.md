# 05 非功能、验收与待确认项

## 1. 非功能需求

以下指标为需求验收基线草案；带“暂定”的数值须在容量和部署形态确认后冻结。

### 1.1 安全与隐私（SPEC-NFR-SEC）

| 编号 | 优先级 | 需求 |
|---|---:|---|
| NFR-SEC-001 | P0 | 所有受保护访问在服务端认证和授权，租户、组织、设备、文件、字段和 AI 工具均不能只依赖前端控制。 |
| NFR-SEC-002 | P0 | 传输中的敏感数据加密，密码、令牌、密钥和连接凭据采用专门的安全存储及轮换机制。 |
| NFR-SEC-003 | P0 | 浏览器、LLM、普通日志、导出文件和前端配置不得包含数据库、ThingsBoard 或对象存储管理凭据。 |
| NFR-SEC-004 | P0 | 文件上传、批量导入、外部接口和 AI 输入均视为不可信输入，执行类型、大小、内容、Schema 和权限校验。 |
| NFR-SEC-005 | P0 | 人员、权限、审计、设备控制和批量导出等敏感能力执行最小权限、强化审计和必要的重新认证/审批。 |
| NFR-SEC-006 | P0 | 备份、缓存、搜索/向量索引、日志和测试数据遵守与源数据一致的租户隔离和数据等级。 |
| NFR-SEC-007 | P0 | 安全事件包括登录攻击、越权、异常导出、敏感工具滥用、提示注入和凭据使用异常，并可告警和追踪。 |
| NFR-SEC-008 | P0 | 每次受保护访问同时校验租户状态、租户应用授权、用户应用权限和数据范围；应用前端不可绕过共享底座直接扩大权限。 |

### 1.2 性能与容量（SPEC-NFR-PERF）

| 编号 | 优先级 | 暂定验收目标 |
|---|---:|---|
| NFR-PERF-001 | P0 | 常用业务列表/详情在正常负载下 P95 不高于 2 秒，普通写操作 P95 不高于 3 秒（不含文件传输和异步任务）。 |
| NFR-PERF-002 | P0 | 设备/组织树采用分页、懒加载或等效机制，规模增长时不一次加载全部对象。 |
| NFR-PERF-003 | P0 | IoT 写入与趋势查询遵守 02 文档的时序性能基线，并可按写入和查询分别扩展。 |
| NFR-PERF-004 | P0 | 大批量导入、导出、报告、OCR、诊断和跨设备长周期查询异步执行，显示进度并可查询最终结果。 |
| NFR-PERF-005 | P0 | AI 工具开始执行后 2 秒内展示已受理/进度状态；模型或工具耗时不阻塞普通业务接口。 |
| NFR-PERF-006 | P0 | 必须通过容量测试验证峰值写入、在线查询、告警、批任务和 AI 并发组合负载。 |
| NFR-PERF-007 | P0 | 容量确认后冻结可复现测试画像：持续/补传写入点秒、波形流量、数据规模、并发查询、聚合粒度、最大返回点数、接收确认边界、测试时长及业务 P95 允许退化。 |
| NFR-PERF-008 | P0 | 容量画像还须冻结峰值持续时间、补传量/恢复时限、实时与补传优先级、测量到可查询/规则事件/通知的端到端延迟、并发看板订阅、OCR 页/分钟、任务队列等待和数据产品传播延迟。 |
| NFR-PERF-009 | P0 | 验证租户噪声隔离：单个租户的高频写入、大查询、批量 OCR/ETL 或 AI 峰值不得突破配额并使其他租户核心 SLO 无界退化。 |

容量冻结前需要下列业务输入：

~~~text
设备总数
有实时接入设备数和占比
每设备平均/最大点位数
各类点位平均/最高上报频率
平均和峰值写入点/秒
单样本大小及图片/文件产生量
原始、分钟、小时聚合保留期
并发在线用户、并发看板和 AI 用户数
最长在线查询时间范围和最大导出范围
并发看板/实时订阅数及可接受端到端延迟
重连补传最大积压量和目标恢复时限
OCR 页数/分钟、并行任务数和可接受排队时间
~~~

计算基准：

~~~text
日样本数 = Σ（启用点位数 × 86400 ÷ 上报周期秒）
峰值写入 = 平均写入 × 峰值系数 + 重连补传
原始容量 = 日样本数 × 单样本存储成本 × 原始保留天数 × 副本/索引系数
~~~

| NFR-AVL-002 | P0 | 外部系统、ThingsBoard 或模型暂时不可用时，平台显示真实状态并支持安全重试/补偿，不伪造成功。 |

## 2. 端到端验收场景

### E2E-AC-001 组织、用户与权限

租户管理员创建组织、人员、账户和角色，把人员设置为设备责任人；该用户登录后只能查看授权组织/负责设备，直接访问其他地址、文件或 AI 查询均被拒绝并留痕。

### E2E-AC-002 无实时接入设备

用户从物理结构模板创建设备，在减速机节点关联说明书和检验图片。设备显示“未接入/不适用”而非离线，但可完成巡检、检验、隐患、工单和维修业务。

### E2E-AC-003 模板化接入

管理员选择接入模板，把共享 PLC 的源点位映射为稳定业务测点，再绑定到两台设备的不同结构节点；预检后进入试运行，真实数据验证通过后分别断言“接入生命周期=已启用”“数据运行状态=正常”“接入覆盖=部分或完整”，三者不混为一个状态。

### E2E-AC-004 时序和新鲜度

用户查询某工作循环的趋势，结果只包含该时间窗并显示单位、质量、测量/接收时间。上报延迟后状态变化，暂停接入后不再产生中断技术事件。

### E2E-AC-005 监测到处置

一个有效业务测点触发技术规则事件并按策略形成业务告警，责任人收到通知并确认；告警下钻到结构节点、实际部件和趋势，随后形成维修/隐患任务，处理、复查、关闭均保留来源和时间线。

### E2E-AC-006 诊断和评估

用户发起健康/故障/风险评估，结果包含输入范围、覆盖率、算法/规则版本和证据；数据不足时不输出无条件正常结论，人工复核后可形成后续任务。

### E2E-AC-007 AI 查询

普通用户询问设备当前状态。AI 仅查询其授权数据，说明接入状态、新鲜度、覆盖和来源；涉及无权人员字段时脱敏，所有消息和工具调用关联该用户。

### E2E-AC-008 AI 录入

用户上传巡检记录并描述问题，AI 生成结构化草稿和缺失项；用户修改确认后调用正式 API。记录可反查用户、会话、消息、模型、工具、前后值和审计编号。

### E2E-AC-009 AI 高风险申请

用户要求修改权限或发送设备命令，AI 不直接执行，只生成带风险说明的申请；重新认证/审批后由确定性流程执行或拒绝，全过程关联发起、确认、审批和技术身份。

### E2E-AC-010 权限撤销与历史

撤销用户权限后，其旧页面、下载地址、AI 会话、缓存和历史工具计划立即不能再访问原资源；其此前业务和审计记录仍保留并显示当时身份快照。

### E2E-AC-011 故障隔离

模型不可用时，用户仍能人工操作设备、工单和告警；ThingsBoard 短暂不可用时业务平台说明数据可能过期，恢复同步后不串设备、不重复写入。

### E2E-AC-012 范围一致性

用户从组织/场景统计下钻到设备和服务，所有数量、列表、报告和 AI 汇总使用同一授权范围与统计时间，不出现原型中的独立随机数据集。

### E2E-AC-013 租户与应用授权隔离

平台管理员创建租户 A 和租户 B，并分别开通数据采集处理、智能运维应用。两个租户可以存在相同用户名和设备业务编号，但登录、接口、缓存、文件、时序、任务、搜索/向量索引、AI 和审计均不能串租户；未开通的应用入口和接口不可访问。

### E2E-AC-014 同租户双应用共享身份

租户 A 的普通用户登录一次后，可按自身权限进入已开通的两个业务应用；切换应用不创建第二套账户、角色或组织关系，撤销某应用权限后仅该应用不可访问，共享账户和另一应用权限保持正确。

### E2E-AC-015 采集处理到运维消费

管理员在共享底座只创建设备和物理结构实例一次。数据采集处理应用把上传文件或实时点位绑定到同一设备/结构节点，经 OCR/清洗/审核形成带来源和版本的数据产品；智能运维应用通过正式接口读取该数据产品，引用同一 `equipmentId`、`structureNodeId` 和来源链。

### E2E-AC-016 平台运维支持访问

平台管理员默认看不到租户业务数据；经授权进入限时支持模式时必须填写原因、限定租户和范围，退出或到期后权限立即失效，所有查看、导出和变更均关联平台人员、目标租户、应用及支持会话。

### E2E-AC-017 双应用故障隔离

数据处理任务或智能运维应用不可用时，共享登录和主数据仍可用，另一应用不受影响；恢复后任务可安全重试，不能重复生成数据产品、告警或工单，也不能改变设备与点位的权威标识。

### E2E-AC-018 部件更换与历史归属

用户在同一减速机结构位置拆下部件 A 并安装部件 B 后，结构路径和业务测点保持不变；更换前后的时序、文件、故障和维修记录按生效时间分别关联 A、B，任何查询或 AI 回答均不得把旧部件历史归到新部件。

### E2E-AC-019 技术事件到业务告警

IoT 规则命中形成不可变技术事件，运维应用按策略创建业务告警并完成人工分派/处置；技术事件恢复与业务告警关闭各自保持权威状态，关系、策略版本、实际用户和两条时间线均可追溯。

## 3. 建议交付切片

这是需求依赖顺序建议，不是已经确认的项目排期。`F0` 和 `F1` 是两个业务应用进入正式开发前的共同门槛：

| 切片 | 可交付闭环 |
|---|---|
| F0 底座骨架 | 租户、应用注册/开通、统一登录、API 约定、服务身份、全链路跟踪和基础审计；建立租户隔离自动测试 |
| F1 共享管理 MVP | 组织、位置、人员、账户、角色/数据范围、设备、物理结构模板/实例、通用文件、字典配置和管理端；两个空业务应用可复用同一登录和权限 |
| D1 数据采集闭环 | 数据分类/采集模板、采集批次、文件上传/无数据登记、接入任务、来源追溯和失败重试 |
| D2 数据处理闭环 | OCR/解析、清洗转换、Schema、质量校验、人工复核、版本/血缘和可供其他应用消费的数据产品 |
| I1 IoT 与时序底座 | 数据源/源点位/业务测点/映射、共享 PLC、统一 IoT 接入、时序数据、质量/新鲜度和技术规则事件；运维应用在此基础上管理业务告警，两个应用只消费一个权威数据面 |
| O1 核心运维闭环 | 监测、巡检、检验、诊断评估、通知、工单/维修、隐患闭环和业务统计，逐步替换原型 Mock 数据 |
| A1 AI 只读与知识 | 双应用全员 AI 入口、受控查询、知识检索、来源引用、应用权限和专项审计 |
| A2 AI 录入与操作 | 结构化草稿、R2 确认写入、R3 申请审批、工具治理和质量评估 |

`D1`、`D2`、`I1` 可在 `F1` 稳定后部分并行，但设备、结构、文件、身份和权限不得在业务应用内重复建设。AI 只读工具可在相应业务 API 稳定后提前开发；AI 写工具不应早于目标业务 API、权限和审计规则。

## 4. 已确认决策与待确认项

### 4.1 已确认决策

| 编号 | 已确认决策 | 规格结论 |
|---|---|---|
| DEC-001 | 多租户范围 | 按单部署、共享数据库的逻辑多租户建设；首期普通账户最多一个有效租户成员身份，不提供租户切换。 |
| DEC-002 | 首期登录方式 | 使用租户编码/租户入口 + 用户名 + 密码；预留 SSO/MFA，高风险操作可要求重新认证或 MFA。 |
| DEC-030 | 建设顺序 | 先搭建可独立运行的通用底座，再接入数据采集处理和智能运维两个业务应用。 |
| DEC-031 | 共享范围 | 两应用共用租户、应用授权、身份、组织、位置、人员、权限、设备、物理结构、文件、字典配置、审计和 AI 治理。 |
| DEC-032 | 数据权威面 | 只建立一个 IoT/时序权威接入与查询面；第二项目文档中的 EMQX/TDengine 方案与 ThingsBoard 均为选型输入，不形成两套权威数据链路。 |
| DEC-033 | 应用开通方式 | 共享管理底座为必备能力；数据采集处理和智能运维应用按租户分别开通，并继续受用户角色权限控制。 |
| DEC-034 | 区域与组织 | 厂区、车间、作业区等按物理位置 Location 管理；集团、公司、部门、班组等管理组织单独建模，二者可关联但不混为同一棵树。 |
| DEC-035 | 既有数据迁移 | 当前阶段不考虑两个原型的数据迁移；原型 Mock/本地数据不进入新底座，正式数据从新底座开始建立。 |

### 4.2 阻塞架构和数据设计

| 编号 | 待确认问题 | 草案默认建议 | 影响 |
|---|---|---|---|

#### 对 DEC-037 的说明：什么是“首批数据产品”

“数据产品”不是原始 PDF、图片或一条传感器数据，而是数据采集处理应用把原始资料识别、整理、校验和人工复核后，形成的稳定结构化结果，供智能运维应用通过 API 使用。

建议首期只跑通三条链路：

1. 检验报告：设备/结构/部件、检验日期、机构、结论、不合格项、下次检验日期、原报告和复核人；
2. 点巡检记录：检查时间、人员、检查项、结果、异常部位、严重度、图片/原文和确认状态；
3. 故障/维修记录：故障部位、现象、原因、处理措施、更换部件、停机时间、维修结果和来源文件。

这样可以直接验证“上传文件 → OCR/解析 → 人工复核 → 发布结果 → 运维侧形成提醒、问题或维修历史”的完整闭环。设备出厂参数、法规知识和其他资料分类后续再增加，不阻塞首期底座。

#### 对 DEC-038 的说明：什么是“IoT 组件职责组合”

该问题不是要求同时部署多个产品，而是避免同一份遥测数据在 ThingsBoard、EMQX、TDengine 中各存一份且都被认为是权威。

建议首期采用最简链路：

~~~text
普通联网设备 ── MQTT/HTTP/CoAP ───────────┐
                                           ├─> ThingsBoard CE + PostgreSQL
PLC ── Modbus/OPC UA ─> ThingsBoard Gateway ┘              │
                                                          ▼
                                                平台统一遥测 API
                                                  ├─ 数据应用
                                                  └─ 运维应用
~~~

- ThingsBoard 负责设备/网关连接、接入凭据、连接状态、遥测接收与查询、技术规则事件；
- 共享底座仍是租户、人员、组织、位置、公共设备、物理结构、业务测点、权限和审计的唯一权威；
- 两个业务应用只调用平台统一遥测 API，不直接使用 ThingsBoard 管理账号或数据库；
- 首期暂不引入独立 EMQX、Neuron 和 TDengine，减少重复消息链路、重复存储和运维成本；
- 如果真实 PLC 协议、边缘处理、消息规模或时序性能验证不满足，再分别评估 Neuron、EMQX 或 TDengine；引入时必须重新明确唯一写入者和权威查询入口。

ThingsBoard 使用的 PostgreSQL 应与共享底座业务数据库保持逻辑隔离，是否共用数据库集群在部署设计阶段决定。
