# 00 产品范围与统一约定

## 1. 产品目标

建设面向高风险起重装备的共享平台底座，在统一租户、身份权限、组织位置、设备结构、文件数据和审计之上，承载“设备数据采集处理”和“智能运维与事故防控”两个业务应用。先完成通用底座，再逐步实现数据归集/治理与监测、诊断、维修等业务闭环。

平台同时服务两类设备：

- 有实时或周期数据接入的设备，可使用在线监测、趋势、告警、诊断和评估能力；
- 无实时数据接入的设备，仍可使用设备档案、物理结构、文件、图片、巡检、检验、隐患、工单、维修和知识服务。

## 2. 目标用户与职责

角色名称不作为写死的权限实现，最终以“权限动作 + 数据范围”组合授权。下列角色用于描述典型用户：

| 典型角色 | 主要职责 |
|---|---|
| 平台管理员 | 管理租户、平台级配置、安全策略和全局审计 |
| 租户/集团管理员 | 管理本租户组织、人员、用户、角色、设备和业务配置 |
| 企业/厂区管理员 | 管理授权组织分支内的设备、人员和业务 |
| 设备管理员 | 建档、维护结构、关联资料、配置接入和责任关系 |
| 数据采集人员 | 按设备、结构、分类和日期上传或接入原始数据 |
| 数据处理/复核人员 | 管理 OCR/ETL 任务、处理数据质量、复核和发布结构化结果 |
| 运行/安全管理人员 | 查看状态、告警、风险、隐患及闭环进度 |
| 巡检/检验人员 | 接收任务、录入记录、上传报告和处理异常 |
| 维修人员 | 接收工单、记录维修过程、备件与结果 |
| 技术/评估人员 | 查看监测数据并开展诊断、健康与风险评估 |
| 审计人员 | 在独立授权下查询操作、数据访问和 AI 审计 |
| 普通业务用户 | 在授权范围内查看设备、使用服务和 AI 助手 |
| 外部系统 | 通过受控接口接入数据或交换业务信息 |

人员档案与登录账户是两个概念：没有账户的人员也可以作为责任人、执行人或报告签署人；有账户的用户通过关联人员档案获得业务身份。

边界约定：

- 共享底座是租户、账户、组织、位置、人员、权限、公共设备/结构、文件身份和审计的权威来源。
- 数据采集处理应用是采集批次、处理任务、OCR/结构化结果和数据谱系的权威来源。
- 智能运维应用是监测业务、诊断评估、风险隐患、工单维修等运维记录的权威来源。
- IoT 底座负责协议接入、连接管理、遥测接收和可选规则处理，不替代完整业务平台。
- AI 助手代表当前用户使用受控工具；任何底层服务账号均不能掩盖真实发起用户。
- 浏览器、LLM 和外部不可信内容不得直接获得数据库或 IoT 管理凭据。

## 4. 本期范围

### 4.1 基础平台

- 租户、组织、人员、用户账户；
- 应用注册、租户应用授权和统一应用入口；
- 组织与物理位置分离管理；
- 角色、功能权限、数据范围和字段级敏感信息控制；
- 菜单、字典、参数配置；
- 文件与资源、通知、待办和系统任务；
- 登录日志、操作审计、数据访问审计和 AI 专项审计；
- 对外接口账号及调用审计。

### 4.2 设备与 IoT

- 设备类别和设备主档；
- 设备物理结构模板、版本、实例和实例差异；
- 结构节点与传感器、PLC 点位、文档、图片及业务记录的关联；
- 接入模板、数据源、测点/标签、映射和连接状态；
- 有实时、无实时、部分接入设备的统一表达；
- 当前值、历史时序、数据质量、新鲜度、告警和查询；
- 与 ThingsBoard 的业务边界和标识映射。

### 4.3 数据采集处理

- 按设备、结构节点、分类和日期采集文件/数据；
- 历史文件导入、无数据声明和采集批次；
- 图像预处理、OCR、文档解析、结构化、清洗和质量校验；
- 人工复核、版本化发布和原始数据到数据产品的谱系；
- IoT 接入配置与运行质量工作台，但不自建第二套设备/时序主数据。

### 4.4 智能运维业务服务

- 场景与组织范围内的设备浏览；
- 安全监控、健康监测、点巡检、检验；
- 健康评估、裂纹预测、故障诊断、风险定量评估；
- 维修、基础数据、供给/制造质量追溯；
- 检验检测、法律法规和常用标准知识库；
- 原型中已有但服务分类尚需确认的“隐患排查”和“问题处理”（历史模块名称）能力。

### 4.5 AI 助手

- 所有有效用户可进入 AI 助手；
- 查询设备、结构、IoT、人员、组织、权限解释、工单、文档及业务统计；
- 从自然语言、文档和图片辅助形成结构化录入草稿；
- 在用户授权和风险策略内调用注册 API；
- 查询、工具调用、确认、审批和业务变更的全链路用户关联审计。

## 5. 暂不默认纳入本期的范围

以下内容并非永久排除，但在业务确认前不视为首期承诺：

- 自研底层设备协议栈以替代成熟 IoT 平台；
- AI 自主修改权限、自主控制设备或执行任意 SQL/HTTP/脚本；
- 完整三维建模工具、CAD 编辑器或高精度物理仿真求解器；
- 面向公众的开放注册和匿名 AI；
- 未明确业务目标的区块链、数据交易或跨平台模型训练；
- 原型中没有业务规则依据的自动诊断结论直接替代人工责任判断。

## 7. 统一术语

| 术语 | 本 Spec 定义 |
|---|---|
| 租户 | 普通用户、设备、文件和业务数据的安全隔离边界；首期一个普通账户只属于一个租户 |
| 应用 | 在共享底座上注册并授权给租户的业务入口，当前包括数据采集处理和智能运维 |
| 组织 | 集团、公司、部门、班组等管理关系，不等同物理厂区 |
| 位置/区域 | 园区、厂区、车间、作业区、安装点等物理空间 |
| 设备/设备实例 | 真实业务中的一台装备，拥有独立编码、组织归属、责任关系和生命周期；即使没有数据接入也存在 |
| 设备类别 | 对同类设备的分类，例如桥式起重机、门式起重机 |
| 物理结构模板族 | 对某类设备组成层级的稳定模板身份，例如“桥式起重机标准结构”；用于归集多个版本 |
| 模板版本/修订 | 模板族中的一次完整定义，状态可为草稿、审核中、已发布、已废止；已发布版本是不可原位覆盖的快照 |
| 结构节点实例 | 某台设备中的稳定物理位置、功能层级或不可替换结构，可独立关联测点、文件和业务记录 |
| 可更换部件资产 | 安装在结构节点上的可独立追踪实物，如带型号/序列号的减速机、制动器；更换不改变结构路径，安装关系带生效时间 |
| 数据源 | 实际产生或转发数据的连接对象，如 PLC、网关、传感器直连或第三方平台 |
| 源点位/标签 | PLC、网关或第三方系统中的技术地址/标签，不直接等同稳定业务语义 |
| 传感器通道 | 可选的物理传感器输出通道，用于连接源点位与业务测点并追踪校准/更换 |
| 业务测点 | 稳定表达“某设备/结构/部件的某个观测量”，与源地址通过带生效时间的映射关联 |
| 接入模板族及版本 | 用于快速配置数据源、点位、映射、质量和告警规则；采用与结构模板相同的“稳定模板族 + 不可覆盖发布版本”语义 |
| 物理结构模型 | 描述设备“由什么组成”，不等同于 IoT 平台中的属性、遥测和命令模型 |
| 实时接入 | 以支持当前状态为目的、按已声明服务等级持续到达的流式或短周期数据；普通日/周周期批采不能仅因定时执行就称为实时 |
| 部分接入 | 只有部分预期结构节点或测点有有效数据 |
| 数据新鲜度 | 以测量时间、接收时间和预期周期判断数据是否仍可代表当前状态 |
| 数据产品 | 经明确 Schema、质量校验和复核发布，可供其他应用稳定消费的版本化结果 |
| 业务 API/AI 工具 | 已注册、可授权、可校验和可审计的确定性能力，不是任意数据库或网络访问 |
| 实际发起用户 | 在登录会话中提出 AI 请求并对操作负责的真实用户 |
| 技术执行身份 | 底层服务调用 API 时使用的服务账号；不能替代实际发起用户 |

## 8. 设备与接入状态模型

### 8.1 设备业务生命周期

建议至少包括：草稿、在役、停用、报废。最终状态和转换规则待业务确认。

### 8.2 设备运行状态

建议至少包括：未知、运行、待机、停机、维护、故障。运行状态必须带来源和更新时间，可以来自实时点位、人工确认或外部系统；没有实时接入的设备不得把长期未更新的人工状态描述为“当前状态”。

设备运行状态不得由数据连接状态直接推导：有数据不一定代表设备运行，无数据也不一定代表设备停机。

### 8.3 数据采集方式

| 状态 | 含义 |
|---|---|
| 无接入 | 仅有设备及业务资料，没有数据源 |
| 人工录入 | 用户在表单中录入离散数据 |
| 文件批量 | 从文件导入历史或批次数据 |
| 周期采集 | 按预期周期持续上报 |
| 流式采集 | 连续或高频上报 |

### 8.4 接入生命周期

| 状态 | 含义 |
|---|---|
| 未配置 | 尚未建立可运行的接入配置 |
| 已配置 | 配置已保存但尚未启用 |
| 验证中/试运行 | 静态和连通性预检已完成，正在使用真实数据验证格式、映射、时间及质量 |
| 已启用 | 预期接收持续数据 |
| 已暂停 | 人工暂停，不应判定为数据中断 |
| 已退役 | 接入不再使用，但保留历史 |

### 8.5 数据运行状态

| 状态 | 适用条件 |
|---|---|
| 不适用 | 无实时接入、暂停或已退役 |
| 等待数据 | 已启用但尚未收到首条有效数据 |
| 正常 | 数据在预期时限内到达且质量可用 |
| 延迟 | 超过允许延迟但尚未达到中断阈值 |
| 中断 | 超过中断阈值 |
| 异常 | 连接、解析、映射或质量校验失败 |

设备页面必须同时展示“业务生命周期、设备运行状态及其来源/更新时间、是否接入/覆盖范围、接入生命周期、数据运行状态、最后测量时间、最后接收时间和数据质量”。不得把未接入显示为离线，也不得用一次文件导入把设备显示为实时在线。

## 9. 权限统一规则

一次受保护访问的有效范围至少由以下部分共同决定：

~~~text
当前租户
∩ 当前应用已授权且用户可进入
∩ 用户有效角色和动作权限
∩ 组织 / 位置 / 本人负责 / 指定设备等数据范围
∩ 目标资源及字段策略
∩ 当前业务状态
∩ AI 工具许可与风险策略（若通过 AI）
~~~

页面隐藏按钮不是授权措施。普通页面、直接 API、批量导入、文件下载、通知跳转和 AI 工具调用都必须由服务端按相同业务权限重新判断。

## 10. 需求假设

本草案采用以下基线：

- 已确定支持简单逻辑多租户；首期一个普通账户只属于一个租户，不支持跨租户资源共享；
- 首期使用租户编码/租户入口 + 用户名 + 密码登录，预留 SSO/MFA；
- 先建设共享底座，再让数据采集处理和智能运维两个应用接入；
- 组织和物理位置分别建模，均为可配置层级；
- 厂区、车间、作业区按物理位置管理，管理组织单独维护；当前不迁移两个前端原型的 Mock/本地数据；
- 人员档案默认最多关联一个有效登录账户，是否允许多账户待确认；
- ThingsBoard 作为优先候选 IoT 底座；Intelligent_data_agent_LE 原设计中的 EMQX/Neuron/TDengine 需要统一评估，不同时建设两套权威设备/时序数据平面；
- AI 写操作默认“先形成草稿或变更预览，再由用户明确确认”；
- 权限变更、用户停用、批量敏感修改、设备控制等默认只允许 AI 发起申请，不允许模型自主执行；
- 所有事实型 AI 回答必须标注来源和数据时间，实时数据不足时必须说明限制。
