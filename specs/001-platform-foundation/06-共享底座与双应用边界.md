# 06 共享底座与双应用边界

## 1. 决策摘要

本版需求新增以下已确认方向：

1. 高风险起重装备智能运维平台与 Intelligent_data_agent_LE 数据采集处理平台不再各自建设用户、组织、设备和权限系统。
2. 先建设一套可独立运行的共享底座，再让两个业务应用接入。
3. 共享底座首期支持简单多租户，而不是完整 SaaS 商业化多租户。
4. 设备、物理结构、文件、数据源和点位等公共主数据只维护一份。
5. 数据采集处理平台负责“数据进入、处理和形成可信数据产品”；智能运维平台负责“使用这些数据开展监测、诊断、评估和运维闭环”。
6. 两个应用通过共享服务/API 和事件使用同一数据身份，不允许前端或应用直接读取对方私有表。
7. 首期普通账户只属于一个租户，使用租户编码/入口 + 用户名 + 密码登录。
8. 厂区、车间、作业区作为物理位置，管理组织使用独立组织树。
9. 当前不迁移两个原型的 Mock/本地数据，正式数据从新底座建立。

## 2. 两个项目的定位

| 应用 | 主要职责 | 不再自行建设 |
|---|---|---|
| 数据采集处理平台 | 设备资料采集、文件归档、图像预处理、OCR、结构化、清洗、聚类、处理任务、结果复核；PLC/传感器数据接入工作台 | 租户、账户、组织人员、通用角色权限、设备主标识、公共文件元数据、公共审计 |
| 智能运维平台 | 场景设备浏览、安全/健康监测、巡检检验、诊断评估、风险、维修、问题工单、知识和用户 AI 助手 | 同上，也不复制数据采集处理平台的原始文件和结构化结果 |
| 共享底座 | 简单多租户、统一身份、组织人员、位置、应用授权、角色权限、设备与结构、数据身份、文件资源、字典配置、通知/待办索引、审计、AI 安全边界 | 不承载某个业务应用特有的页面流程、任务状态机或算法结论 |

## 4. 简单多租户定义（SPEC-SMT-01）

### 4.1 首期采用的简化

- 一个部署实例服务多个逻辑租户。
- 每个普通业务账户首期只属于一个租户，不提供跨租户切换。
- 一个租户可有多级组织、人员、位置、设备，并可启用一个或两个业务应用。
- 平台运营管理员与租户用户分离；平台管理员默认不能浏览租户业务数据。
- 使用共享服务和共享存储的逻辑隔离，不要求每租户独立数据库、独立部署或独立域名。
- 不做租户自助注册、计费套餐、在线购买、跨租户协作和复杂租户级定制。

### 4.2 功能要求

| 编号 | 优先级 | 需求 |
|---|---:|---|
| SMT-FR-001 | P0 | 平台运营管理员可创建、编辑、启用、停用和归档租户，维护租户编码、名称、状态、有效期和联系人。 |
| SMT-FR-002 | P0 | 租户成员及其组织、人员、位置、设备、结构、数据源、点位、文件、任务、业务记录、AI 会话和审计都必须归属一个租户。 |
| SMT-FR-003 | P0 | 普通业务账户首期只关联一个租户；需要跨租户工作的人员使用不同租户账户，不复用会话。 |
| SMT-FR-004 | P0 | 登录通过租户编码/租户入口与用户名共同确定租户，服务端从认证结果注入 tenantId，客户端参数不能覆盖。 |
| SMT-FR-005 | P0 | 所有租户级唯一规则都包含租户范围，例如设备业务编码、用户名、组织编码、位置编码和模板编码。 |
| SMT-FR-006 | P0 | 数据库查询、缓存键、对象存储路径、消息主题、搜索/向量索引、异步任务和 IoT 映射均执行租户隔离。 |
| SMT-FR-007 | P0 | 租户停用后禁止新登录、数据接入、文件上传、AI 调用和普通业务写入；历史及审计按策略保留。 |
| SMT-FR-008 | P0 | 平台管理员进入租户支持模式必须选择目标租户和原因、获得授权、限时有效并全程强化审计，不存在默认跨租户查询。 |
| SMT-FR-009 | P0 | 任何租户业务后台任务、服务账号和 AI 工具调用均携带确定的租户上下文；平台级任务使用明确 PLATFORM 作用域，触达租户资源时还必须有受控 targetTenantId，缺少或冲突时拒绝执行。 |
| SMT-FR-010 | P1 | 支持租户配额和用量统计，包括用户、设备、文件空间、处理任务、IoT 和 AI 用量；首期可以只告警不计费。 |
| SMT-FR-011 | P0 | 平台运营账户、应用目录和平台级模板/配置采用明确 PLATFORM 作用域；对租户执行支持操作时同时记录 actorTenantId（可空/平台）与 targetTenantId，不能借空 tenantId 绕过隔离。 |

## 5. 应用注册与统一入口（SPEC-APP-01）

共享底座至少注册三个应用标识：

- foundation-admin：共享管理控制台；
- data-processing：设备数据采集处理应用；
- intelligent-maintenance：智能运维应用。

| 编号 | 优先级 | 需求 |
|---|---:|---|
| APP-FR-001 | P0 | 平台维护应用编码、名称、状态、入口、权限目录和可用能力。 |
| APP-FR-002 | P0 | 按租户授予应用使用权；租户未启用的应用不能显示、登录或调用 API。 |
| APP-FR-003 | P0 | 用户在租户已启用应用中仍须通过角色获得具体菜单、动作和数据权限。 |
| APP-FR-004 | P0 | 同一用户登录一次后可在获权应用间切换，不重复维护账号；切换应用须校验应用授权并记录 applicationId。 |
| APP-FR-005 | P0 | 认证上下文至少包含 tenantId、userId、会话、当前应用或调用方、有效权限版本和跟踪编号。 |
| APP-FR-006 | P0 | 角色可包含共享底座权限和某个应用的权限；数据范围规则在两个应用间使用同一组织、位置和设备身份。 |
| APP-FR-007 | P0 | 应用停用后禁止新入口和新调用，但不删除该应用产生的业务数据或公共资源关联。 |
| APP-FR-008 | P1 | 统一应用启动页可显示用户有权使用的应用、待办、通知和最近访问。 |

## 7. 组织与位置不能混为一体

已确认共享底座必须把管理组织与物理位置拆分：

- Organization：法律、管理或部门关系，例如集团、公司、部门、班组；
- Location：物理位置关系，例如园区、厂区、车间、作业区、设备安装位置；
- Equipment relation：设备分别关联资产组织、使用组织、维保组织和安装位置。

厂区、车间、作业区统一按 Location 管理；集团、公司、部门、班组按 Organization 管理。数据权限可按组织、位置或指定设备授权，二者可建立责任/管辖关系，但不能仅因名称相同就合并。

| 编号 | 优先级 | 需求 |
|---|---:|---|
| SHR-FR-010 | P0 | 组织和位置各有独立树、编码、生命周期及历史，不共享同一实体表述。 |
| SHR-FR-011 | P0 | 设备必须有明确租户，可分别关联组织责任和物理安装位置。 |
| SHR-FR-012 | P0 | 数据范围支持组织及下级、位置及下级、本人负责和指定设备集合，并可组合。 |
| SHR-FR-013 | P0 | 位置调整不自动改变人员组织，组织调整也不自动迁移设备物理位置。 |

## 10. 两个现有原型的接入与未来迁移约束

本阶段已确认不迁移两个原型中的 Mock、localStorage 或其他本地演示数据。新底座从正式租户、组织、位置、用户和设备建档开始；以下内容仅作为未来确有外部真实数据需要导入时的约束，不属于 F0/F1 交付范围。

### 10.1 迁移映射

| 现有概念 | 共享底座目标 | 迁移规则 |
|---|---|---|
| 数据平台 areaLevel1/areaLevel2 | Location | 厂区/车间/作业区按物理位置导入，不进入管理组织树 |
| 运维平台集团/板块/分厂 | Organization 或 Location | 逐节点标注管理组织或物理位置后迁移 |
| 两边 device.id | Equipment 内部 ID + ExternalIdentity | 保留旧 ID 作为来源标识，生成公共内部 ID |
| realtime/static、online/offline | 采集方式、接入生命周期、数据运行状态、设备运行状态 | 按明确规则拆分，无法判断时标记未知 |
| 生命周期文件 | Resource/File + Association | 保留设备、分类、归档日期、上传人和原始来源 |
| mock ETL 结果 | 非生产演示数据 | 不进入正式租户；如保留则放演示租户并标记 synthetic |
| 两边本地用户 | UserAccount/Person | 去重需人工确认；不得仅按显示名自动合并 |

### 10.2 迁移要求

| 编号 | 优先级 | 需求 |
|---|---:|---|
| MIG-FR-001 | P1 | 未来如启动迁移，先创建租户、组织、位置和用户映射，再导入设备、文件和业务记录。 |
| MIG-FR-002 | P1 | 每批迁移生成批次号、来源、输入摘要、成功/失败/冲突清单和执行用户审计。 |
| MIG-FR-003 | P1 | 迁移支持试运行、重复执行幂等和回滚/作废标记，不直接覆盖已确认公共对象。 |
| MIG-FR-004 | P1 | 对同一出厂编号、注册号或业务代码的候选重复设备展示证据，由授权用户合并或保留。 |
| MIG-FR-005 | P1 | 迁移完成后两个应用用公共 ID 查询同一设备、文件和数据结果，旧 ID 仍可追溯。 |
| MIG-FR-006 | P1 | 迁移期可提供旧 ID 解析兼容层，但新增数据必须使用公共 ID。 |

## 11. 共享底座首期交付范围

### 11.1 Foundation MVP（先建设）

首期必须交付：

1. 租户管理与租户启停；
2. 统一登录、会话和租户上下文；
3. 应用注册、租户应用授权和用户应用入口；
4. 组织、人员、账户、位置；
5. 角色、权限、组织/位置/设备数据范围；
6. 设备类别、公共设备主档、外部标识；
7. 物理结构模板/实例、可选可更换部件及安装历史基础能力；
8. 文件元数据、版本、ACL 和设备/结构关联；
9. 字典、参数、统一审计和基础通知/待办；
10. 服务身份、应用间调用及对两个应用开放的版本化公共 API。

首期可暂不实现：

- OCR/ETL 的全部算法能力；
- 现场协议和高频时序的完整生产接入；
- 运维诊断算法和风险模型；
- AI 写操作；
- 复杂审批流、计费、跨租户用户和每租户独立部署。

### 11.2 完成定义

共享底座首期完成必须同时满足：

- 平台管理员创建租户 A、B，并分别启用不同应用组合；
- 两个租户的管理员独立管理组织、位置、人员、用户、角色和设备；
- 同一租户用户一次登录后按权限进入数据应用和运维应用；
- 一台设备只建档一次，两个应用看到相同 ID、名称、结构和文件；
- 跨租户通过页面、直接 API、文件地址、任务参数和 AI 工具均不能访问；
- 所有关键操作能按租户、应用、用户和设备追溯；
- 任一业务应用不可用时，共享底座和另一应用仍可登录及工作。

## 12. 端到端验收

- SHR-AC-001：租户 A、B 都存在 deviceCode=CRANE-001 时互不冲突，任何查询都只返回当前租户对象。
- SHR-AC-002：租户 A 用户只获数据应用权限时看不到运维应用，直接调用运维 API 被拒绝。
- SHR-AC-003：同时获两个应用权限的用户切换应用无需再次登录，但每次调用记录正确 applicationId。
- SHR-AC-004：数据应用创建公共设备并上传检验报告后，运维应用使用同一设备 ID 查看该文件，不产生第二份设备或文件。
- SHR-AC-005：数据应用完成 OCR/结构化并发布结果后，运维应用通过受控数据产品查询，能追溯原文件、处理版本和复核人。
- SHR-AC-006：租户同时建立管理组织树和物理位置树；厂区/车间属于位置，人员部门属于组织，修改其中一棵树不自动改变另一棵树。
- SHR-AC-007：运维应用更新设备专属诊断记录，不向公共设备主表写入未注册字段。
- SHR-AC-008：后台 ETL 任务缺少 tenantId 或 applicationId 时拒绝执行并记录安全事件。
- SHR-AC-009：平台管理员未进入授权支持模式时无法查看任何租户设备；进入后操作带原因、时限和审计。
- SHR-AC-010：从审计中可还原“用户在数据应用上传文件—处理服务生成结果—用户在运维应用发起评估”的完整链路。

## 13. 后续架构选型约束

本文件不直接锁定实现产品，但后续选型必须满足：

- 只建设一套身份/RBAC/租户底座，不能在两个应用各部署一套用户表再同步；
- 只建设一套公共设备、结构、文件和点位身份；
- 只确定一套权威 IoT/时序数据平面。既有 ThingsBoard 倾向与另一项目文档中的 EMQX/Neuron/TDengine 方案需要统一评估，不能默认并行成为两套权威数据源；
- 数据处理服务可以独立扩展计算资源，但必须使用共享任务、文件、设备和审计上下文；
- 前端可保持两个业务应用的风格和页面结构，共享管理控制台及基础组件应统一。
